# Lock In v2.1: Gym tab plan

2026-10-12 · Armin Memišević

## Goal and scope

The Gym tab lets you log workouts as exercises, sets, reps and weight, start them from saved routines, and see how often you train. It is built after v2 ships (after Task 20) and does not change the 22-task v2 plan.

**In scope**
- Log a workout: pick exercises from a bundled database or your own, enter weight (kg) and reps per set, flag warm-up sets.
- Routines: save a workout as a routine, start it later with weights and reps prefilled from your last performance.
- History: past workouts, editable and deletable.
- Stats: gym visits per week and month against a target, sets per muscle group per week, best set per exercise over time.
- A simple in-app rest countdown.
- Works offline, data stays on the phone, included in export and import.

**Out of v2.1**
Supersets, plate calculator, rest-timer notifications, exercise images and instructions, body-weight log, social features, AI suggestions, cloud sync.

## Navigation: six icon-only tabs

The tab bar becomes six icons with no text, like Instagram. Do this in v2.1 (task G7), not in v2: v2 ships with the labels in the approved design, and one task then changes the bar.

- **Width is fine.** On a 375 to 390 pt wide iPhone, six tabs are about 62 to 65 pt each, above the 44 pt minimum tap target.
- **Active state must work without a label.** Filled icon plus accent colour for the active tab, outline for the others.
- **Accessibility.** Every icon button keeps an `aria-label` with the old tab name, so VoiceOver still reads it.
- **Design override.** The approved reference PNGs show labels, and CLAUDE.md says the design and PNGs win. G7 first adds one line to CLAUDE.md recording that you chose icon-only, so the audit does not flag it as a deviation.
- **Icons.** Reuse the existing icon set from the design package; the Gym icon is a dumbbell drawn in the same stroke weight. No new icon library.
- **Risk.** Icon-only bars are harder to learn; the Gym and Analytics icons must be clearly different at a glance. You judge this on the iPhone at the G7 checkpoint.

## Data model and storage

Gym data lives under its own localStorage key, `lockin.v2.gym`, separate from `lockin.v2`. Task 5's review showed that invalid state in the main key gets the whole save moved to `lockin.v2.corrupt` on the next launch. A gym bug must never be able to do that to your challenge data.

```
{
  v: 1,
  settings: { weeklyTarget: 4 },
  customExercises: [ { id: "custom-1", name, muscle, equipment } ],
  routines: [ { id, name, createdAt, items: [ { exerciseId, sets: [ { reps, weight } ] } ] } ],
  workouts: [ { id, date: "YYYY-MM-DD", startedAt, finishedAt: number | null,
                name, routineId: string | null,
                items: [ { exerciseId, sets: [ { reps, weight, warmup, done } ] } ] } ]
}
```

**Conventions, same as the v2 core**
- Pure functions: state and `nowMs` in, new state out. No direct Date use in core files; the forbidden-date-API grep applies to the new files.
- A refusal returns a code and leaves the state byte-identical.
- Lookups by id use a `Map` or `Object.hasOwn`. Every id-taking function gets a test with `toString` and `__proto__` as ids (the Task 5 inherited-key bug).
- Setters take `null`, never `undefined`.

**`validateGym` rules**
- `v` is 1; every collection is an array; ids are non-empty strings, unique within their collection.
- `reps` is an integer from 1 to 999. `weight` is a finite number from 0 to 1000 (0 allowed for bodyweight).
- `date` is a real calendar date. `finishedAt` is `null` or a number at least `startedAt`.
- A workout whose `finishedAt` is set must have at least one done, non-warm-up set.
- At most one workout has `finishedAt: null`.
- A workout may reference an exercise id that no longer exists in the bundled list. That is not invalid; the UI shows "Unknown exercise".

**Load path.** Invalid or unparseable gym data moves to `lockin.v2.gym.corrupt`, the Gym tab starts empty and shows a one-line notice, and the rest of the app is unaffected. Loading never throws.

## Rules

Every rule has a hand-computed example. Core tests (G3 to G5) must assert exactly these values, written by hand before the code, not copied from the code's output.

| Rule | Definition | Hand-computed example |
|---|---|---|
| Gym visit | A local calendar date with at least one finished workout. Unfinished workouts never count. | Finished workouts on Mon 2026-10-05, Wed 10-07 (two of them), Sun 10-11, Mon 10-12. Week of 10-05 = 3 visits (dates 05, 07, 11). Week of 10-12 = 1. October so far = 4. |
| Week | Monday to Sunday, built from date keys, never by adding 7 x 24 h. | The week containing Sun 2026-10-25 (EU clocks go back) has 7 date keys, Mon 10-19 to Sun 10-25. Tested with TZ=Europe/Sarajevo via spawnSync. |
| Finish | Needs at least one done, non-warm-up set; otherwise refused with `no-sets`. Discard is always allowed. | A workout with only a done warm-up set cannot be finished. |
| One open workout | Starting a workout while another has `finishedAt: null` is refused with `workout-open`. | Start, start again: second call returns `workout-open`, state unchanged. |
| Stale open workout | An open workout from an earlier date is shown on launch with Finish or Discard. Never auto-finished, never auto-deleted. | Open since yesterday 22:00: still open today, offered both buttons. |
| Volume | Sum of weight x reps over done, non-warm-up sets. | 80 x 8, 80 x 8, 77.5 x 7 = 640 + 640 + 542.5 = 1822.5 kg. |
| Sets per muscle | Count of done, non-warm-up sets, credited to the exercise's primary muscle only. | Bench 3 working sets + 1 warm-up, pushdown 3 sets: chest 3, triceps 3. |
| Estimated 1RM | Epley, weight x (1 + reps / 30), rounded to 0.1 for display only. 1 rep = the weight. Only done, non-warm-up sets with weight > 0 and 1 to 10 reps. | 80 x 5 = 93.3. 60 x 10 = 80.0. 100 x 1 = 100. 50 x 12 and 0 x 15 are excluded. |
| PR | A set whose estimated 1RM is strictly higher than every earlier qualifying set of that exercise, ordered by `startedAt`. The first ever performance is the baseline, not a PR. | Best so far 93.3: 82.5 x 5 = 96.25 is a PR; 80 x 5 again = 93.3 is not. |
| Prefill | Adding an exercise or starting a routine prefills set rows (done = false) from the most recent finished workout containing that exercise, warm-ups excluded. Set count = the routine item's count, or last time's count when added by hand. Set i takes last time's set i; beyond that, last time's final set. No history: the routine's template values, else one empty set. | Routine: bench, 4 sets. Last time 80 x 8, 80 x 8, 77.5 x 7. Prefill = 80 x 8, 80 x 8, 77.5 x 7, 77.5 x 7. |
| Save as routine | From a finished workout: exercise order and working-set counts, template reps and weight from that workout, warm-ups excluded. | A workout with 3 exercises, 4 + 3 + 3 working sets, becomes a routine with those counts. |
| Repeat last workout | A new open workout with the same exercises as the latest finished workout, prefilled by the Prefill rule. | Latest workout had bench and rows: the new one has bench and rows, nothing done. |
| Weekly target | Integer 1 to 7, default 4. Visits are compared to it; there is no streak and no penalty. | 3 visits against 4: shows 3/4. |

## Exercise database

The app bundles a trimmed copy of [free-exercise-db](https://github.com/yuhonas/free-exercise-db): a public-domain (Unlicense) set of 800+ exercises with name, equipment, primary and secondary muscles, category, instructions and images. It is never fetched at runtime, because gym signal is unreliable and an API dependency would break the offline app.

- **Build script, run once by hand.** `scripts/build-exercises.mjs` reads the dataset's combined `exercises.json` and writes `data/exercises.json` with only `id`, `name`, `equipment`, `primaryMuscles[0]` and `category`. The committed file is what ships. `data/exercises.SOURCE.md` records the dataset commit hash and a credit line.
- **Size.** The checkpoint reports raw and gzipped size. Budget: 200 KB raw. Over budget, you decide what to drop.
- **Offline.** The file is precached in `sw.js`.
- **Gaps in the data.** The dataset allows `null` for equipment, force and mechanic on some exercises. The build script maps a null equipment to "other"; search must never crash on a missing field.
- **Search.** Client-side. Every typed word must appear in the name, case-insensitive. Filter chips for muscle and equipment. The last 10 used exercises appear first, then the rest alphabetically. Custom exercises are merged in and marked.
- **Custom exercises.** Name 1 to 60 characters after trim, unique case-insensitively across bundled and custom, a primary muscle from the dataset's muscle list, an equipment value from the dataset's equipment list. Ids are `custom-1`, `custom-2` and so on. Rename is allowed; delete is not (decision 9).
- **Ids that vanish.** If a future dataset refresh drops an id, history shows "Unknown exercise" and nothing breaks. Refreshing is manual only, as a reviewed commit.
- **Muscle and equipment lists** are read from the dataset by the build script and committed, not typed by hand.

## Workflow, risks and carry-overs

**Workflow.** Same as v2. One task per session. Failing WIP tests are committed first and never edited. A reviewer subagent runs before the PROGRESS entry. You paste the raw checkpoint here, I verify it, then write the push prompt. Pushes are fast-forward only to the `gym` branch. No force-push, no amend, no push to `main`. On Windows there is no `TZ=... node`; tests use spawnSync.

**Skills per prompt.** Core tasks G1 to G6: `superpowers:subagent-driven-development`, `superpowers:test-driven-development`, `superpowers:verification-before-completion`, `ponytail:ponytail`. UI tasks G7 to G11 add `playwright-cli`, `mobile-native`, `apple-design`, `emil-design-eng`, and `break-ui` for worst-case data. All design skills are audit-only. G12 adds `mattpocock-skills:code-review`.

**Public repo.** No real workouts, routines, bodyweight or program content committed. Test data is invented. The exercise dataset is public domain and may be committed.

**Risks**
- **Logging friction decides whether you use it.** If a normal set takes more than one tap with prefilled values, you will stop logging. G9 is judged on the iPhone with a real workout, not on screenshots.
- **History is the data you would mind losing most.** G6 extends the v2 backup reminder to gym data. Export before every release.
- **Dataset quality.** Some names are odd or near-duplicate. Custom exercises and search ranking are the answer, not cleaning the dataset by hand.
- **Icon-only bar.** Judged at G7. If it fails on the phone, the fallback is to take Gym out of the bar and reach it from the Today card.
- **Scope creep.** Anything in the out-of-scope list needs a new decision and a new task, not a quiet addition inside an existing one.

**Carry-overs from v2 that apply here**
- Views pass `Date.now()`; core never reads the clock.
- Import must refuse non-string fields, wrong types and impossible dates, and leave both storage keys untouched on refusal.
- Every loop over stored keys skips unknown keys safely and keeps them in state.
- Worst-case data for UI checks: 60 exercises in a workout, 20 sets on one exercise, a 60-character exercise name, an empty history.
